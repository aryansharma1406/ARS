# ARS website QA report

Date: 14 September 2026
Target: http://localhost:3000
Status: PARTIAL. Public-browser, anonymous API and automated checks completed. Authenticated end-to-end acceptance is blocked pending dedicated Customer, Staff, Owner and Admin test logins and confirmation of payment test mode.

No application functionality was changed. No live charges, marketing sends, account creation or real guest check-ins were performed. Existing public event data was used for browsing. Automated database tests use isolated fixtures.

## Findings

Severity: P1 = release blocker; P2 = functional/quality defect; P3 = minor issue. Type-check findings are compile-time defects, not claims that the corresponding development pages crashed.

### QA-01: Admin venue analytics fails TypeScript checking
- Severity: P1.
- Page: /admin/performance/[venueId].
- Reproduce: From the repository root run `./node_modules/.bin/tsc --noEmit --incremental false`.
- Actual: Four TS18048 diagnostics at app/admin/(portal)/performance/[venueId]/page.tsx:36 and :45: `venue` is possibly undefined inside renderRange.
- Expected: The application type-checks successfully, retaining missing-venue handling.
- Recommended fix: Pass the narrowed venue into renderRange, or bind a definitely defined value after the notFound guard so the nested function preserves narrowing.
- Evidence: Compiler output. Production build was not run; Next configuration does not opt out of build type checking.

### QA-02: Customer OTP rate-limit error uses an unsupported status type
- Severity: P1.
- Page/API: /login, /api/auth/customer-otp.
- Reproduce: Run the same TypeScript command.
- Actual: TS2345 at app/api/auth/customer-otp/route.ts:38: status 429 is not accepted by AuthError's status union.
- Expected: Rate limiting can return a correctly typed 429 response.
- Recommended fix: Add 429 to the shared error contract if supported by its serializer, or use the existing typed rate-limit response mechanism. Add coverage for the rate-limited branch.
- Evidence: Compiler output and route source. A real OTP provider rate limit was not intentionally triggered.

### QA-03: Dead digital-pass JSX blocks type checking
- Severity: P1.
- Page/component: My Pass / digital pass, components/DigitalTicketCard.tsx:175.
- Reproduce: Run the TypeScript command.
- Actual: TS2769 for new Date(ticket.scanned_at) where the value may be undefined. The diagnostic is in a duplicate `false && ticket.scanned_at` block.
- Expected: Pass rendering type-checks and displays the scanned timestamp once.
- Recommended fix: Remove the unreachable duplicate block; retain the existing guarded timestamp display.
- Evidence: Compiler output and component source. Authenticated pass display was not exercised.

### QA-04: Native scanner type error leaks into website compilation
- Severity: P1.
- Surface: Website build scope and apps/staff-scanner/src/Scanner.tsx:154.
- Reproduce: Run the root TypeScript command.
- Actual: TS2551: StyleSheet.absoluteFillObject is unavailable in the installed React Native types. The website's root check includes the native app.
- Expected: Both projects pass their own type checks, with intentional separate compilation boundaries.
- Recommended fix: Use the supported absolute-fill style API in the scanner and separate website/native TypeScript scopes. Keep an independent scanner type-check in CI rather than hiding its error.
- Evidence: Compiler output. No Android/iOS device test was performed in this website audit.

### QA-05: Genre filter UI contradicts the active URL filter
- Severity: P2.
- Pages: /events?category=Bollywood and /events?category=Techno.
- Reproduce: Open the homepage, then click the footer Bollywood or Electronic link. Inspect the genre dropdown on the events page.
- Actual: The dropdown says `All music genres`, but the URL/category filter is active. Bollywood returned an empty list; Electronic returned two matching events. The current options are derived from exact categories in the catalog, whereas these links use category values that are not exact options.
- Expected: The control represents the actual applied genre, even when no events match.
- Recommended fix: Normalize category identifiers across footer links and filters, or include the selected query value in the options. Preserve a visible selected filter in empty states.
- Evidence: Browser reproduction and app/events/page.tsx source. An empty Bollywood catalog alone is not a bug.

### QA-06: Partner page overflows narrow mobile viewports
- Severity: P2.
- Page: /partner.
- Reproduce: Open the page with a narrow mobile viewport, around 312 CSS pixels; scroll to the contact panel and venue form.
- Actual: document.documentElement.scrollWidth was 327 while innerWidth was 312. A narrower follow-up also showed the aside, email link and form extending to approximately x=327.7. This produces horizontal overflow.
- Expected: Content fits the viewport with consistent side padding and no horizontal scrolling.
- Recommended fix: Give grid/flex children min-width:0, constrain form controls to available width, wrap the email link, and reduce narrow-screen padding if needed. Validate at 320 and 375 CSS pixels and with text zoom.
- Evidence: Read-only DOM measurements. The test browser scales requested viewport dimensions; figures above are the actual measured CSS viewport, not the requested preset.

### QA-07: Existing automated suite is not a reliable release gate
- Severity: P2 (test infrastructure/coverage).
- Surface: `npm test`.
- Reproduce: Run npm test from the repository root.
- Actual: 90 passed, 17 failed across 107 tests; five test files passed and four failed.
- Failure breakdown: authorization 11; customer-auth 1; catalog 4; setup-sql 1.
- Diagnosis: Authorization mocks do not model new portal-session checks and tier requirements; callback expectations predate the location/onboarding redirect; catalog tests mock the old data source; setup SQL expects 12 tables but sees 17.
- Additional gap: The database test setup applies migrations 0001 and 0002, not the full current migration chain. Its passing isolation tests do not certify newer tiers, coupons, marketing, promoter or portal-session behavior.
- Recommended fix: Update fixtures/mocks and intended assertions, apply all migrations to the isolated test database, and add current cross-role and concurrent-scan integration tests. Do not weaken security checks merely to satisfy stale tests.
- These 17 test failures are NOT counted as 17 confirmed website defects.

## Additional risks and source-only observations

### WhatsApp permission is preselected
- Surface: /login, Mobile OTP.
- Browser steps: Open Mobile OTP and inspect the offers/event-updates checkbox before interacting.
- Observed: Marketing permission is checked by default.
- Risk: Users can submit without actively choosing marketing consent. This is an intentional earlier requested setting, not an accidental regression; no legal compliance conclusion is made here.
- Recommendation: Prefer unchecked, explicit opt-in with an audit record of the user's action and easy opt-out. Keep OTP service messages separate.

### Unexposed default price ceiling
- Surface: /events, app/events/page.tsx.
- Source observation: Without a price query parameter, priceMax defaults to 10000 and participates in filtering, while the page does not expose a matching price control.
- Potential reproduction: In an isolated test dataset, publish an otherwise eligible event above INR 10,000 and open /events without query parameters.
- Potential impact: The event disappears from discovery without an explanation.
- Recommendation: Default to no price ceiling unless a user-selected limit is present, or expose and label the limit.
- Not reproduced against current real data; no event was created or repriced for this audit.
